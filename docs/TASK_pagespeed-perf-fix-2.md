## 0. 배경 (1차 작업 이후 재측정 결과)

- 1차 작업(`adsbygoogle.js`를 `beforeInteractive` → `lazyOnload`로 전환)으로 LCP 하위 지표인 "요소 렌더링 지연"은 2,460ms → 250ms 수준으로 크게 개선됨. 이 부분은 효과가 확인됐고 되돌리지 않는다.
- 그러나 같은 URL(퇴직소득세 계산기 페이지, 모바일)을 동일 조건으로 5회 연속 재측정한 결과:

| 측정 | 성능 점수 | LCP | LCP 분석 하위파트 합계 |
|---|---|---|---|
| 1회차 | 72 | 12.1초 | 250ms |
| 2회차 | 54 | 18.8초 | 2,350ms |
| 3회차 | 65 | 14.0초 | 1,320ms |

- **핵심 이상 징후**: 매 측정마다 "LCP 분석" 섹션의 하위 파트(첫 바이트+요소 렌더링 지연) 합계는 250ms~2,350ms 수준으로 정상 범위인데, 정작 상단에 표시되는 최종 LCP 값은 12~19초로 전혀 다르다. 이 불일치가 3회 모두 동일한 패턴으로 재현됨.
- **해석**: "LCP 분석" 박스는 최초 감지된 LCP 후보(디스클레이머 텍스트 블록)의 렌더링 통계만 보여주고 있고, 실제 최종 LCP로 채택되는 요소는 이후 등장하는 다른 요소로 추정된다. `lazyOnload`로 미뤄둔 애드센스 스크립트가 브라우저 유휴 시간에 실행되면서 광고 슬롯(`<ins class="adsbygoogle">`)이 화면에 새로 삽입되고, 이게 텍스트 블록보다 면적이 커서 "새로운 최대 콘텐츠"로 재지정되고 있을 가능성이 가장 유력하다.
- **결론**: 1차 조치(로딩 타이밍을 "페이지 인터랙티브 이후"로 미룸)만으로는 부족하다. 광고 슬롯이 로드되는 "시점"이 아니라, 로드되는 "트리거 조건" 자체를 "사용자가 실제로 그 위치까지 스크롤했을 때"로 바꿔야 한다.

## 1. 절대 규칙 (CLAUDE.md 재확인 + 1차 지시서 규칙 계승 + 이번 작업 특칙)

1. 서버·DB·외부 API 추가 금지. 완전 정적 유지 (`output: 'export'`)
2. **애드센스 광고 코드 내용(스크립트 src, pub ID, 슬롯 data 속성)·ads.txt는 절대 수정하지 않는다.** 이번 작업도 "언제/어떤 조건에서 로드를 트리거하냐"만 바꾼다.
3. 1차 작업에서 적용한 `lazyOnload` 자체는 유지한다(되돌리지 않음). 이번 작업은 그 위에 "뷰포트 진입 시에만 스크립트 실행을 트리거"하는 조건을 추가로 얹는 것.
4. Google Tag Manager / GA4는 이번 작업 범위 아님 (1차에서 이미 정상 확인됨, 건드리지 않음)
5. 계산 로직(`lib/calculators/*.ts`), 세율표, ToolGuide 본문 콘텐츠는 절대 수정하지 않는다
6. **광고 슬롯의 화면 내 위치(페이지 내 순서, 상단/하단 배치)는 T1 조사 결과를 먼저 보고한 뒤에만 변경 여부를 판단한다.** 임의로 위치를 옮기지 않는다 — 위치 변경이 필요하다고 판단되면 코드 변경 전에 반드시 조사 결과를 먼저 공유하고 승인받는다.
7. localStorage/sessionStorage 금지
8. 새 npm 패키지 추가는 최소화한다. Intersection Observer는 브라우저 네이티브 API이므로 별도 라이브러리 없이 구현 가능 — 라이브러리 추가가 필요하다고 판단되면 먼저 왜 필요한지 보고하고 승인받는다.
9. 커밋 접두어: `perf:`

## 2. 작업 목록

### T1. 광고 슬롯 위치 및 초기 노출 여부 조사 (조사 우선, 코드 변경 전)

퇴직소득세 계산기 페이지 기준으로 다음을 확인하고 보고한다:
- 광고 슬롯(`<ins class="adsbygoogle">` 또는 관련 컴포넌트)이 코드상 어느 컴포넌트/파일에 있는지
- 페이지 내에서 몇 번째 위치에 배치되어 있는지 (계산기 UI 위/아래, ToolGuide 본문 앞/뒤 등)
- **뷰포트 최초 진입 시점(스크롤 0)에 이 슬롯이 이미 화면에 보이는 위치인지, 스크롤을 내려야 보이는 위치인지** — 이게 이번 작업의 핵심 분기점이다. 만약 최초 진입 시점에 이미 화면 안에 있다면 뷰포트 기반 지연 로딩 자체가 무의미하므로, 그 경우 T1 결과만 보고하고 T2로 넘어가지 않는다(별도 판단 필요).

### T2. Intersection Observer 기반 지연 로딩 구현 (perf:) — T1에서 "스크롤이 필요한 위치"로 확인된 경우에만 진행

- 광고 슬롯을 감싸는 컨테이너에 `IntersectionObserver`를 적용해, 해당 컨테이너가 뷰포트에 가까워질 때(권장: `rootMargin: '200px'` 정도로 살짝 여유를 둬서 스크롤 중 자연스럽게 로드되도록)만 `adsbygoogle.js` 로드 및 `(adsbygoogle = window.adsbygoogle || []).push({})` 호출을 트리거한다.
- 구현 방식 예시(참고용, 프로젝트 컨벤션에 맞게 조정):
  - 광고 슬롯 컴포넌트를 클라이언트 컴포넌트로 분리(이미 그렇다면 유지)
  - `useEffect` + `IntersectionObserver`로 컨테이너 관찰 시작
  - 교차 감지 시 1회만 스크립트 로드/푸시 실행 (관찰 해제)
  - 스크립트가 이미 전역에 로드되어 있는 경우(다른 페이지에서 먼저 로드된 경우) 중복 로드 방지 로직 포함
- **주의**: 이 구현은 광고 슬롯이 그려지는 "DOM 요소 자체"는 그대로 두고(레이아웃 시프트 방지를 위해 빈 슬롯이라도 자리는 유지), 그 안에서 실제 광고 스크립트가 언제 요청되느냐만 바꾸는 것이다. 슬롯 자체를 조건부 렌더링(마운트/언마운트)하면 CLS가 새로 발생할 수 있으니, 슬롯 컨테이너는 항상 렌더링하고 내부 스크립트 실행만 지연시킨다.

### T3. 재측정 방법 표준화

- 이번 작업의 검증은 **단발성 측정 1회로 판단하지 않는다.** 배경에서 확인했듯 동일 조건에서도 점수가 50~70점대로 크게 흔들렸다.
- 배포 후 PageSpeed Insights(모바일, 퇴직소득세 계산기 페이지)를 **최소 5회 연속 측정**하고, 5개 점수와 5개 LCP 값을 모두 기록한다. 최저/최고/중앙값을 함께 보고한다.

### T4. LCP 후보 재지정 여부 확인

- 재측정 시 "LCP 분석" 섹션의 하위 파트 합계와 상단 최종 LCP 값이 이번에도 크게 어긋나는지 확인한다.
- 만약 이번에도 어긋난다면, 브라우저 개발자 도구의 Performance 패널이나 Lighthouse의 상세 트레이스에서 실제로 어떤 DOM 요소가 최종 LCP 후보로 잡혔는지 직접 확인하고 캡처해서 보고한다(광고 슬롯이 맞는지, 다른 요소인지 확정).

  한 재발 가능성은 여전함.
- **측정 방법 자체의 한계 확인 (08-12, 운영자 검토 후 추가 검증)**: 코드 확인(운영자 요청 1) —
  전체 저장소 grep 결과 `adsbygoogle`/`push(`/`data-ad-` 관련 코드는 `app/layout.tsx`의 `<Script
  src=".../adsbygoogle.js?client=...">` 한 줄뿐. `enable_page_level_ads` 등 별도 push() 설정도,
  `<ins data-ad-slot>` 수동 슬롯도 코드에 전혀 없음 — Auto Ads는 코드가 아니라 애드센스 계정
  설정만으로 켜져 있는 것으로 재확인(1차 지시서가 이미 기록한 FundingChoices 동의배너의 자동
  주입 패턴과 동일 메커니즘).
  네트워크 스로틀링 검증(운영자 요청 2) — 스로틀링 미적용 vs Slow 4G+4x CPU 적용을 A/B 대조한
  결과: TTFB는 10ms → 11~13ms로 거의 그대로인 반면, 렌더 지연은 176ms → 1,100~1,464ms로
  4x CPU 슬로다운과 일치하게 늘어남. **CPU 스로틀링은 정상 작동했지만, 이 MCP 툴의 "Slow 4G"
  프리셋은 대역폭만 일부 제한할 뿐 실제 왕복 지연(RTT)은 사실상 주입되지 않는 것으로 확인** —
  진짜 Slow 4G라면 TTFB가 최소 수백 ms는 늘어야 함. 즉 위 5회 참고 측정은 CPU는 느리게
  재현했지만 네트워크 지연은 공식 PageSpeed Insights보다 훨씬 관대한 조건이었고, Auto Ads
  채움 지연으로 인한 LCP 재지정을 재현하기에 애초에 부족한 조건이었을 가능성이 큼. 따라서 이
  로컬 트레이스 결과는 "문제 재현 안 됨"의 근거로 쓸 수 없고, 공식 PageSpeed Insights로만
  신뢰 가능한 검증이 됨.
- 미완/이슈: `docs/DECISIONS.md` O-05로 오픈 이슈 등록. 근본 해결책은 코드가 아니라 AdSense
